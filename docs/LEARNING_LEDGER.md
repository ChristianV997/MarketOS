# Learning Ledger v1

The Learning Ledger is MarketOS's deterministic memory of decisions and outcomes. It records what was tried, the evidence used, the result, why it worked or failed, and the bounded next action. It is the learning layer beneath the Resource & Execution Governor; it is not a database, vector store, analytics collector, or autonomous optimizer.

## Why it exists

A company improves when wins are repeatable, losses are not repeated, and inconclusive tests are treated as requests for better evidence. Learning events turn product validation, supplier proof, creative tests, landing-page tests, provider dry runs, model routing, TrustOS reviews, and portfolio decisions into structured lessons.

The default ledger is synthetic and offline. It uses placeholders and sanitized fixtures, never real client data, live metrics, prompts, credentials, provider payloads, or external calls.

## Core records

Every `LearningEvent` links a source decision, department, workspace scope, evidence references, action, cost assumption, metrics, outcome, confidence, reasons, winner/loser attributes, do-not-repeat rules, iteration recommendations, and an optional `provider_id` (empty unless the event actually concerns a specific provider). `LearningExperiment` adds the hypothesis, metric, kill/scale thresholds, and learning requirement needed before another iteration.

Outcomes are `win`, `loss`, `inconclusive`, `killed`, `scaled`, `paused`, `iterated`, `blocked`, `needs_more_evidence`, and `invalid_test`. Failure and success taxonomies are deliberately bounded so aggregation remains deterministic and reviewable.

## Rules and recommendations

Losses and blocked actions can produce `LearningDoNotRepeatRule` records such as: require a hypothesis and kill rule before an ad experiment; do not use frontier reasoning for low-evidence work; do not retry a provider after its cap without new evidence; and do not create a new site when an existing brand can absorb the test. Rules carry severity, block behavior, review period, source event, and client visibility.

**Recovery-pass-2 repair:** the recovered source's rule/recommendation text was keyed almost entirely off `event.failure_reasons[0]`, and several categories this doc already described had no matching entry — they silently fell through to a generic "the same failure reason recurs without changed evidence" fallback. `invalid_test_design` (incomplete ad experiment design), `poor_offer`, `poor_margin`, and `trust_blocker` now have explicit iteration-recommendation text (`poor_margin`/`trust_blocker` already had do-not-repeat text; `poor_offer`/`invalid_test_design` had neither). "Absorbable new website" and "scale without evidence" have no dedicated `FAILURE_REASONS` value at all — they are compound conditions checked against `event.action_taken` (`create_new_website`, `scale_ad_budget`) before the reason-keyed map, so those two categories are represented without adding a new taxonomy value. A provider-specific retry-cap violation (`runaway_guard_triggered` + `action_taken=run_provider_data_pull`) is now distinguished from the generic runaway-workflow rule it previously shared text with.

`LearningIterationRecommendation` records the smallest next change: improve a creative angle, fix an offer or page, obtain supplier proof, revisit unit economics, complete terms/privacy evidence, attach TrustOS control-plane evidence, use a cheaper model tier, or capture missing learning before continuing.

## Governor feedback

`LearningDecisionInfluence` is a fixed sample handoff contract for the Resource & Execution Governor: seven hardcoded example scenarios illustrating how prior wins can support a controlled scale decision, prior losses reduce priority or create a kill/soft-block, missing learning blocks another iteration, and recurring TrustOS or provider blockers require evidence completion. It does not depend on the events actually reported (it is sample data, not a query over `events`), and it does not mutate Governor behavior or authorize execution.

Portfolio impacts summarize working and failing categories, hooks, offers, price points, landing-page patterns, supplier types, provider usefulness, and recurring TrustOS blockers. Model-routing impacts record when algorithmic, local, cheap, frontier, or human review was sufficient. Provider impacts distinguish useful dry runs from terms, privacy, schema, budget, or approval blockers.

### Learning capture, interpretation, and Governor influence (v1.1 bridge)

The recovered v1 module stopped at reporting; it had no path from a real report's events into an actual Governor decision. This adds one, kept deliberately narrow:

1. **Learning capture** stays exactly what it was: `LearningEvent` records, one per experiment/decision, produced by `build_learning_ledger_report`. The only capture-side change is a bug fix: `_event()` accepted a `provider` keyword since the original recovery but silently dropped it; it now lands in a real, trailing-default `LearningEvent.provider_id` field (empty by default, so nothing that didn't already pass `provider=` is affected).
2. **Learning interpretation** is `derive_governor_influence(report, *, action_type, candidate_id, workspace_id, proposed_hypothesis, stale_event_ids)`, in `evaluation/companyos/learning_ledger.py`. It inspects the *actual* events and do-not-repeat rules a real report contains for one action/candidate pair -- not the fixed `LearningDecisionInfluence` samples -- and returns a `LearningGovernorInfluence`:
   - `evidence_mode` (`actual` | `simulated` | `unavailable` | `not_run` -- this offline module only ever emits `simulated`, `unavailable`, or `not_run`; `actual` is reserved vocabulary for a future live-evidence source), `confidence`, `recency_label`, `provenance` (the source `learning_event_id`s, capped at `_MAX_MATCHING_EVENTS` so the record stays bounded regardless of ledger history length).
   - `win_count`/`loss_count`, `supports_scale` (repeated, clean wins only), `hold_or_avoid` (repeated failure/blocked/killed), and `kill_blocks_resumption` (a *single* `killed` outcome is definitive and needs no repetition, unlike `hold_or_avoid`).
   - `supports_scale` is additionally withheld -- and the reason recorded in both `rationale` and a dedicated boolean -- when the evidence itself is not trustworthy enough to mean anything: `low_confidence_evidence` when average `confidence` is below `MIN_SCALE_CONFIDENCE` (`0.6`), and `fixture_only_evidence` when `candidate_id` is still the unspecified `PLACEHOLDER_CANDIDATE_ID` sentinel (repeated wins with no real candidate attached are not evidence about any actual decision). Malformed evidence needs no separate check here: `LearningEvent.__post_init__` already rejects an invalid `event_type`/`outcome` before the event can exist at all, so it can never reach `derive_governor_influence` in the first place.
   - `conflicting_evidence`: true whenever the same action/candidate/workspace shows both wins and losses -- `supports_scale` can never be true when this is true, so mixed or contradictory evidence can never read as a green light.
   - `excluded_stale_event_ids`: events a caller explicitly names via `stale_event_ids` (this offline module has no clock of its own to compute staleness, so it never invents one) are removed from every computation below -- win/loss counts, provenance, confidence -- not merely flagged, so a stale win cannot contribute to `supports_scale` and a stale loss cannot contribute to `hold_or_avoid`.
   - do-not-repeat block/override state (`do_not_repeat_blocked`, `do_not_repeat_overridden`, `do_not_repeat_rule_ids`) and a TrustOS-recurrence flag (`trustos_recurrence_blocked`, now computed only from this action/candidate/workspace's own matching events -- see the cross-client note below).
   - Do-not-repeat handling is severity-aware, matching this contract's own `BLOCK_BEHAVIORS` ladder (`warn` < `soft_block`/`hard_block`/`requires_approval`): only a rule whose `recommended_block_behavior` is *not* `"warn"` counts toward `do_not_repeat_blocked`/`do_not_repeat_rule_ids`. A matching `"warn"`-severity rule is still recorded (`advisory_rule_ids`, and a rationale line) but never forces `previous_learning_required` on its own -- the same graduated-severity idea as Dagster's separate WARN/ERROR asset-check thresholds for the same underlying check. No rule in this module's own fixtures currently reaches `"warn"` (`_rule()` only ever emits `soft_block`/`hard_block`), so this is forward compatibility for the existing vocabulary, not a behavior change for any shipped fixture.
   - planning-only recommendations: `recommended_model_tier`/`deprioritize` for model lessons, and `recommended_provider_id`/`avoid_provider_ids` for provider lessons (a provider is only ever recommended if it is not itself flagged in `avoid_provider_ids`), plus `iteration_recommendation` (the matched `LearningIterationRecommendation` text, surfaced for whatever plans the next candidate action -- not consumed by the Governor at all).
   - `fingerprint`: a stable `hashlib.sha256`-based identity over the record's own content, so identical evidence always reproduces the identical fingerprint and any real change in evidence changes it.
   - **Every match is scoped to `workspace_id` first, always** -- events, do-not-repeat rules, and the TrustOS-recurrence count are all filtered to the same workspace before anything else, so a lesson from one client can never influence a decision for another even when `candidate_id`/`action_type` happen to coincide. No matching event yields `not_run` and every boolean `False` -- a candidate with no history in its own workspace gets no influence, by construction.
3. **Governor influence** is `apply_learning_influence(request, influence=None, *, apply_model_routing_lessons=False, apply_provider_routing_lessons=False)`, in `evaluation/companyos/resource_execution_governor.py`. `evaluate_execution_request` itself is unchanged -- every budget, quota, portfolio, experiment-threshold, and TrustOS/workspace check it already ran still runs, unconditionally. The bridge only ever *tightens* one existing field, `previous_learning_required` (reusing the "required learning has not been captured" blocker the Governor already had), when the influence reports a repeated failure, a kill, an unresolved do-not-repeat rule, or a recurring TrustOS/security blocker. A model-tier or provider-id planning lesson is applied only if the caller opts in (`apply_model_routing_lessons`/`apply_provider_routing_lessons`), and even then a provider is only ever switched *away* from one the influence itself flagged in `avoid_provider_ids` -- never used to second-guess an otherwise-fine provider, and never touching `registered_provider`/`terms_privacy_complete`/`output_contract_tested`, budgets, or approval state. `influence` is a plain `Mapping` (`LearningGovernorInfluence.to_governor_context()` returns exactly the seven keys read: `do_not_repeat_blocked`, `hold_or_avoid`, `trustos_recurrence_blocked`, `kill_blocks_resumption`, `recommended_model_tier`, `recommended_provider_id`, `avoid_provider_ids`), so neither module imports the other's types.
4. **Unchanged hard gates:** positive learning (`supports_scale`) and conflicting/stale evidence are computed but never read by `apply_learning_influence` -- they have no code path to bypass anything. `trustos_decision`, `workspace_decision`, `approval_state`, and every budget/quota/provider-readiness field are never touched by the bridge, so a recurring TrustOS/security blocker (or any other hard gate) stays exactly as blocking as it was before this bridge existed, and a positive, conflicting, or stale learning signal cannot move a budget-exceeding, TrustOS-blocked, or provider-unready request past its existing outcome. Callers that never pass `influence` get the original request object back unchanged (`is`, not just `==`).

This keeps the "one event spine, no second Governor/router/scorer" boundary intact: the ledger stays stdlib-only (it still imports nothing from the Governor, and `hashlib` for the fingerprint is stdlib), and the Governor's only new code is one small, additive function that reads a handful of plain-dict keys.

### Bounded public patterns mined for this bridge

No new dependency or framework was adopted (stdlib-only stays a hard constraint). A handful of well-known data-quality/lineage project *contracts* were reviewed and adapted as small, local ideas:

- **OpenLineage's facet/producer model** (atomic, typed metadata attached to a run) is already mirrored by `LearningEvent.source_module`/`source_decision_id` and `LearningGovernorInfluence.provenance` -- confirmed as an existing match, no change needed.
- **Great Expectations' explicit, named freshness expectation** informed keeping `stale_event_ids` as an explicit, caller-declared signal rather than inventing a wall-clock staleness heuristic this offline module has no real clock to compute.
- **Dagster's WARN-vs-ERROR asset-check severity** (two thresholds for the same check, one blocking and one advisory) motivated the do-not-repeat severity fix above: a `"warn"`-severity rule is recorded but does not force `previous_learning_required` the way `soft_block`/`hard_block`/`requires_approval` do.
- **Evidently's reference-vs-current drift comparison** and **Pydantic's discriminated-union/strict-mode validation** were reviewed but not adapted: this module already validates its own controlled vocabularies at construction time (`LearningEvent.__post_init__`, `LearningGovernorInfluence.__post_init__`), and a reference-window drift comparison does not fit this ledger's single-snapshot-per-report shape without inventing new state this module deliberately does not keep.
- **OPA/Rego's "collect every denial reason into one set, default-deny" pattern** was reviewed against `derive_governor_influence` and confirmed as an existing match rather than a gap: `rationale` already accumulates every contributing signal (do-not-repeat, kill, hold/avoid, conflicting/low-confidence/fixture-only evidence, TrustOS recurrence) instead of stopping at the first one, and there is no code path where positive evidence alone produces an "allow" -- `supports_scale` is informational only. Re-verified by direct testing (stacking every negative signal on one candidate at once) rather than assumed.

## Client-safe visibility

The ledger preserves `internal_only`, `workspace_only`, `client_visible_summary`, `aggregated_safe_summary`, and `blocked` visibility. Client-safe summaries contain status, bounded lessons, blockers, evidence requirements, and next actions only. They never expose prompts, formulas, heuristics, source code, global provider intelligence, cross-client learning, credentials, or raw metrics.

**Known vocabulary drift (recorded during the recovery pass, not silently changed):** this `VISIBILITY` tuple is parallel to, but not byte-identical with, `evaluation/trustos/client_workspace_isolation.py`'s `ACCESS_MODES`. `internal_only`, `workspace_only`, and `blocked` match exactly; `client_visible_summary` here corresponds to `client_visible` there; `aggregated_safe_summary` here corresponds to `aggregated_safe_summary_only` there; and `redacted_summary_only` has no counterpart here. The ledger still enforces its own visibility gating and rejects client-private and secret-like input, so this is a consistency gap rather than a leak path. It was left un-renamed because renaming would change the recovered schema and the semantics its tests encode — reconciling the two vocabularies belongs to a follow-up lane that owns both modules.

## Commands

```text
python scripts/run_learning_ledger.py --json
python scripts/run_learning_ledger.py --markdown
python scripts/run_learning_ledger.py --event-type ad_experiment --markdown
python scripts/run_learning_ledger.py --scenario ads_winner_loser --markdown
python scripts/run_learning_ledger.py --scenario frontier_llm_waste --markdown
python scripts/run_learning_ledger.py --output artifacts/learning_ledger/latest --markdown
```

Output is not written unless `--output` is supplied. The CLI rejects secret-like and client-private fixture markers. No database, vector memory, model call, provider call, ad, publishing, payment, order, message, or authentication action exists in v1.

## Future path

Later work may persist approved learning events behind Client Workspace Isolation and a reviewed database/RLS design. That future system must retain provenance, professional-review boundaries, and deletion/retention policy. It must not turn the ledger into autonomous spend, publishing, outreach, or customer-action authority.
